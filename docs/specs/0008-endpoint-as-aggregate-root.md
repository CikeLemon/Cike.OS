# Spec: 接入点升为聚合根（独立端点类、平铺路由与详情接口）

> Triage: `ready-for-agent`
> 术语遵循根 `CONTEXT.md`（模型提供方、接入点、协议、提供商映射、模型）；结构决策见 `docs/adr/0006-接入点升为聚合根.md`（取代 ADR 0005 的三层聚合与其 2026-11-27 修订注记的接口形态）；接口拆分的来龙去脉见 spec 0007（其「聚合」「端点」两节由本 spec 取代）；聚合内子实体的写法、校验三层划分见 `Backend/AGENTS.md`。

> **2026-11-27 取代**：本文整体已由 [spec 0009](./0009-provider-as-connection-with-models.md) 取代——接入点与映射删除，模型成为模型提供方聚合内的子实体，现行结构见 ADR 0007。下文仅作历史记录。

## Problem Statement

模型提供方的「接入点」在代码里是提供方聚合内的子实体：提供方上挂着接入点集合，映射又是接入点下的子实体，形成仓库里唯一的三层聚合。后果是每新增、修改或删除一个接入点，后端都要把整个提供方连同它名下全部接入点与映射（含密钥）加载进内存，为此专门写了一个两级预加载的自定义仓储；接入点自己的工厂是程序集内部可见的，却已经有全局 Id、被 URL 直接指认、有自己的用例与 DTO。重新按聚合边界评估后确认：提供方与接入点之间没有任何需要事务一致性保证的不变量，「接入点名称同提供方内唯一」只是一条按提供方过滤的查重约束。接入点被误判成了子实体，接口也停在「子资源式嵌套路由」的中间态：端点方法寄宿在提供方的端点类里，没有自己的详情接口，约定路由表达不了嵌套路径，只能逐个方法手标路由。

## Solution

把接入点升为聚合根：它只持有所属提供方的 Id，提供方上不再有接入点集合；提供商映射继续做接入点的子实体。接入点拥有自己的端点类，走框架的约定路由，成为平铺的顶层资源：按提供方过滤的列表、单条详情、新建、更新、删除。两级预加载的自定义仓储随三层聚合一起删除，两个聚合都用通用仓储。对管理者可见的行为不变：仍在提供方详情页里维护接入点，一个表单同时装连接信息与全部模型映射；提供方删除时接入点与映射一并删除。

## User Stories

1. 作为管理者，我在提供方详情页看到的接入点表格、新建 / 编辑 / 删除的交互与提示文案与现在完全一样，以便这次调整对我透明。
2. 作为管理者，我新建接入点时指定它属于哪个提供方，并一次提交协议、名称、接入地址、密钥、协议专属字段和它的全部模型映射，以便连接与它能提供的模型一次配好。
3. 作为管理者，我给一个不存在的提供方新建接入点时被拒绝且什么都不保存，以便不会把接入点挂到空气上。
4. 作为管理者，我打开某个接入点的编辑抽屉时，表单里是这个接入点此刻的最新数据，以便别人刚改过的内容不会被我的旧页面覆盖。
5. 作为管理者，我编辑某个接入点并保存时只改动这一个接入点，提供方名下其余接入点不受影响。
6. 作为管理者，编辑接入点时协议不可修改，要换协议只能删掉重建，以便协议专属设置不会错位。
7. 作为管理者，我更新接入点时提交的是它的完整模型映射列表：已映射的模型更新分数与提供商侧模型名，新出现的模型新增，没提交的映射删除，以便映射随接入点一次保存。
8. 作为管理者，我在同一个接入点里把同一个模型映射两次时被拒绝且什么都不保存，以便一个接入点对一个模型只有一条映射。
9. 作为管理者，我可以把同一个模型分别映射到同一提供方的两个接入点下，以便同一个模型既能走 OpenAI 兼容、又能走 Anthropic 兼容。
10. 作为管理者，接入点的映射引用了不存在的模型时被拒绝且什么都不保存，以便映射永远指向真实存在的模型。
11. 作为管理者，同一提供方下两个接入点重名时被拒绝，不同提供方下的接入点可以重名，以便在同一供应商下区分不同连接、又不与别家冲突。
12. 作为管理者，接入点删掉以后，同一提供方下可以用同样的名称再建一个，以便误删后能原样恢复。
13. 作为管理者，新建接入点时提交的协议与设置类型对不上时被拒绝；更新接入点时提交的设置类型与它现有的协议对不上时同样被拒绝，以便保存下来的设置与协议一致。
14. 作为管理者，我不填 OpenAI 的组织标识、不填 Anthropic 的 API 版本也能保存接入点。
15. 作为管理者，我删除一个接入点时它的映射一并删除，之后这些模型就可以被删除。
16. 作为管理者，接入点删到零个后提供方依然存在，以便先立起供应商再逐步配置。
17. 作为管理者，我删除提供方时它名下所有接入点和映射一并删除，以便不留下指向已删除提供方的接入点。
18. 作为管理者，我修改提供方名称时名下接入点与映射原样保留。
19. 作为管理者，我请求一个不存在的接入点的详情时得到「不存在」，别的租户的接入点对我而言同样是不存在，以便既不会读错对象、也看不到别家的连接配置。
20. 作为管理者，按一个不存在的提供方查接入点列表时得到空列表而不是报错，以便页面在提供方已被删除时仍能安静地显示空态。
21. 作为管理者，接入点列表与详情里每个接入点带着它所属提供方的 Id、创建时间与更新时间，以便知道它归谁、什么时候配的。
22. 作为管理者，接入点列表按名称排序、接入点里的映射按分数从高到低并带模型显示名称，以便不认识提供商侧模型名的人也能看懂。
23. 作为管理者，提供方列表页里每个提供方一行，显示它用了哪些协议、支持哪些模型、有几个接入点，这一行为不因本次调整而变化。
24. 作为前端开发者，我执行 `pnpm gen:api` 后拿到的函数覆盖接入点的全部五条路由，组件只从生成层导入，不手写 URL。
25. 作为后端开发者，接入点是聚合根：有自己的静态工厂与意图方法，不再经提供方的集合加入，也不再需要程序集内部可见的工厂，以便实体形状与它的生命周期一致。
26. 作为后端开发者，提供方与接入点两个聚合之间只按 Id 引用，提供方上没有接入点集合，以便没有任何「加载整棵提供方」的代码路径。
27. 作为后端开发者，接入点连同它的一层映射用通用仓储的一级预加载即可读写，不需要为任何一方写自定义仓储，以便少一份基础设施代码。
28. 作为后端开发者，接入点的重名、提供方是否存在、映射引用的模型是否存在集中在用例处理器的单个校验方法里，新建与更新共用，以便规则只写一处。
29. 作为后端开发者，接入点端点类走约定路由，不出现显式指定路由的特性，以便路由形状与仓库里其它资源一致。
30. 作为测试者，我能在不手写 URL 的情况下验证接入点五条平铺路由的动词、路径、查询串参数绑定、校验与业务拒绝两种 400、详情的 404，以及租户隔离。
31. 作为测试者，业务规则（重名、模型不存在、映射同步、级联删除）的测试继续从命令 / 查询这一最高点进入，HTTP 测试不重复它们。
32. 作为未来的实现 agent，我拿到本 spec 即可独立完成全部实现（决策均已定稿），不必再做架构裁决。

## Implementation Decisions

### 后端

- **聚合**：
  - 接入点是租户级聚合根：所属提供方 Id、名称、协议、接入地址、密钥、协议专属设置、映射集合。静态工厂接收提供方 Id 与连接字段；意图方法：修改（名称、接入地址、密钥、协议专属设置——不含协议，协议创建后不可变）、同步映射（以模型为键整体同步，同一模型只出现一次）。修改时断言协议专属设置的子类型与接入点现有协议一致。工厂与意图方法公开，不再限于程序集内部。
  - 提供方是只含名称的聚合根：**删除它上面的接入点集合与所有针对接入点的意图方法**，只剩创建与改名。两个聚合按 Id 引用，外键（所属提供方 Id）在接入点这一侧。
  - 提供商映射不变：接入点聚合内的子实体，工厂与意图方法限于程序集内部，随接入点的新建 / 更新请求整体同步，没有独立接口。
  - 实体、工厂、意图方法内不写任何单字段基础校验。
- **仓储**：两个聚合都用框架通用仓储；删除连同两层子集合加载的自定义仓储接口与实现。接入点连同它的一层映射的读写用通用仓储的一级预加载；接入点删除前必须连同映射加载跟踪，映射才会跟着软删。
- **用例**（接入点五个 + 提供方两个受影响）：
  - 新建命令（新建 DTO，处理后带出新接入点 Id）、更新命令（接入点 Id + 更新 DTO）、删除命令（接入点 Id）、列表查询（提供方 Id，返回接入点 DTO 列表）、详情查询（接入点 Id，不存在时结果为空）。
  - 新建 / 更新共用一个私有校验方法：所属提供方必须存在（仅新建需要，更新不改归属）；名称在该提供方名下互不重复（更新时排除自身）；映射引用的模型去重后一次计数核对。被拒时什么都不保存。
  - 列表与详情：只读加载接入点（连同映射），实体到 DTO 交给 Mapster，接入点按名称排序、映射按分数降序，模型显示名称一次批量取回回填。列表按提供方 Id 过滤，提供方不存在时返回空列表（不再返回「不存在」）。详情不存在（含不属于本租户）时为空。
  - 提供方的删除用例：查出名下全部接入点（连同映射加载）逐个删除后，再删除提供方。提供方的更新用例不变（只改名）。
- **端点**（Service.Open）：
  - 新增接入点的端点类，类级自动校验，全部走约定路由（`api/v1` 前缀）：`GET /ModelProviderEndpoints/List?modelProviderId=`、`GET /ModelProviderEndpoints/{id}`、`POST /ModelProviderEndpoints`、`PUT /ModelProviderEndpoints/{id}`、`DELETE /ModelProviderEndpoints/{id}`。
  - 列表返回 200；详情不存在返回 404；新建成功返回新接入点 Id（long 序列化为字符串）；更新、删除成功返回 200。
  - 提供方的端点类删掉全部接入点方法，不再出现显式指定路由的特性；提供方五个端点不变。
  - 响应形状沿用现状：FluentValidation 失败是 400 + ProblemDetails，业务拒绝是 400 + 消息文本，取不到单条资源返回 404。
- **DTO**：
  - 新建 `CreateModelProviderEndpointDto`：**新增所属提供方 Id**、名称、协议、接入地址、密钥、协议专属设置、映射列表。
  - 更新 `UpdateModelProviderEndpointDto` 不变：不含所属提供方 Id（归属创建后不可变）、不含协议、不含 Id。
  - 输出 `ModelProviderEndpointDto`：**新增所属提供方 Id**，其余不变（继承框架审计基类，含名称、协议、接入地址、密钥、协议专属设置、映射列表）。映射的输入 / 输出 DTO 不变，提供方 DTO 不变。
- **Validator**：新建 DTO 增加一条「所属提供方 Id 必须大于 0」，其余规则沿用；更新 DTO 规则不变。
- **EF 与数据**：接入点的实体映射从「提供方拥有一组接入点」改为「接入点属于一个提供方」（提供方一侧无导航集合）；接入点到映射的集合关系、外键列、索引、删除行为均不变。全部索引仍非唯一。预计生成的迁移不改表结构（仅让模型快照与配置一致）；**若迁移里出现任何改表操作，停下来先报告再继续**。不写数据迁移。
  - **实施结果（2026-11-27）**：迁移 `EndpointAsAggregateRoot` 实际新增了一列 `ConcurrencyStamp`（varchar(40) NOT NULL DEFAULT ''）——来源是聚合根基类自带的乐观并发戳，与其它聚合根一致，是「接入点升为聚合根」的直接后果；外键列、索引、删除行为均未变。该迁移已应用到 dev 库。
- **文档同步**：后端 AGENTS.md 中三条口径改写——聚合边界按不变量划分（没有不变量、却有全局 Id / 独立用例 / 独立接口的子项应升为聚合根，接口随之独立）；「多级子集合的加载走自定义仓储」改为「需要连同一级子集合加载时用通用仓储的一级预加载，两级以上先重新评估聚合边界」；删除「嵌套子资源路由」一条。spec 0007 顶部加修订注记指向本 spec。

### 前端

- **API 层**：后端跑起后执行 `pnpm gen:api` 重新生成，组件只从生成层导入函数与类型，不手写 URL。
- **详情页**：接入点表格改为按提供方 Id 过滤的列表接口；新建 / 编辑 / 删除成功后只刷新列表；提供方不存在（404）仍显示「模型提供方不存在或已被删除」。页面布局、列、交互不变。
- **接入点抽屉**：新建时提交所属提供方 Id；打开编辑时按接入点 Id 拉取详情来回填表单（不再用列表行），拉取失败给出提示且不允许保存。表单字段、协议只读、切换协议二次确认、映射行等交互不变。
- **纯函数层**：「表单 → 新建请求体」增加所属提供方 Id 参数；「表单 → 更新请求体」不变。

## Testing Decisions

- **好的测试**只断言可观察行为：保存后读出来是什么、什么被拒绝、HTTP 响应的状态码 / 内容类型 / 响应体形状；不断言实体私有方法、不依赖 SQL。
- **后端接缝一（业务规则，命令 / 查询）**：沿既有接缝与造数工厂，接入点用例改经它自己的五个用例进入。先例：模型提供方测试类。
  - 归属：给不存在的提供方新建被拒；列表对不存在的提供方返回空；详情对不存在 / 别的租户的接入点为空；修改 / 删除别的租户的接入点按「接入点不存在」被拒。
  - 重名：同提供方下重名被拒且不保存；不同提供方可重名；改名为兄弟接入点的名称被拒；删掉后同名可重建。
  - 协议：更新后协议不变；设置子类型与现有协议不匹配被拒且不改任何东西。
  - 映射：同一接入点重复映射同一模型被拒；同一模型挂同一提供方的两个接入点放行；引用不存在的模型（新建 / 更新）被拒且不保存；更新时映射整体同步（更新 / 新增 / 移除）。
  - 级联：删接入点后其映射不再阻止模型删除、兄弟接入点与映射原样；删提供方后接入点列表为空且模型可删；被引用的模型删除仍被拒。
  - 提供方：改名后接入点与映射原样；提供方详情不再涉及接入点。
- **后端接缝二（HTTP 形状，真实宿主管线）**：沿用 spec 0007 引入的 HTTP 测试宿主与 HTTP 测试类，用例改到平铺路由。
  - 五条路由各自的动词与路径；列表的查询串参数按名绑定（换一个提供方 Id 得到不同结果；不存在的提供方返回空数组）；新建返回字符串形式的 Id 且详情能按它取回；详情不存在返回 404；校验失败 400 + ProblemDetails；业务拒绝 400 + 消息文本；按租户头隔离。
- **EF 行为接缝**：既有的实体映射冒烟测试按新结构改写——接入点作为聚合根插入时自动生成雪花 Id、写入租户；映射随接入点保存拿到 Id、写入租户与外键；一级预加载能把接入点连同映射查全；从接入点移除映射后保存即软删；删接入点连带映射软删；逐个删除接入点再删提供方后两者均为软删。
- **前端**：纯函数接缝（vitest）——表单转新建请求体（含所属提供方 Id）、转更新请求体（不含提供方 Id 与协议）、前端自身校验。浏览器走查兜底：新建提供方 → 跳详情 → 新建两个不同协议的接入点 → 编辑其中一个（详情回填、协议只读）→ 重名被拒 → 删一个 → 删到零 → 改名后接入点仍在 → 删除提供方。
- **验收**：`dotnet build` 0 警告（既有三条除外）、`dotnet test` 全绿；`pnpm gen:api` 后 `pnpm build`（含 vue-tsc）与 `pnpm test` 通过；生成层里接入点五条函数存在、提供方端点类下不再有接入点函数；dev 库真实 HTTP 冒烟通过。

## Out of Scope

- 提供商映射的独立接口或升为聚合根。
- 提供方列表页及其汇总 DTO 的任何改动。
- 接入点的连通性测试、从供应商 API 拉取模型清单。
- `ApiKey` 读取侧脱敏与「留空表示不修改」。
- 调用路由的运行时执行链路。
- 新增协议及其专属字段。
- 仓库里其它聚合（如工具包下的工具）的边界复核。
- 模型、标签、权限体系的任何改动。

## Further Notes

- **发布通道**：本仓库的 issue tracker 与 triage 标签词表仍未配置（`docs/agents/` 不存在、本机无 gh CLI），本 spec 沿前例以仓库内 markdown 落盘并标注 `ready-for-agent`。
- **设计来源**：接口形态与聚合结构由 2026-11-27 的设计讨论定稿，ADR 0006、ADR 0005 的修订注记与 `CONTEXT.md` 已先行更新；代码仍是「三层聚合 + 嵌套路由 + 自定义仓储」的中间态（spec 0007 的未提交实现），以本 spec 为准在其上修改。
- **风险一（一级预加载）**：框架通用仓储的一级预加载在仓库里尚无使用先例，只有框架文档背书。落地第一步先在 EF 冒烟测试里验证「接入点连同映射一次查全」；若不可用，再为接入点补一个只做这一件事的自定义仓储，并在交付说明里注明原因。
- **风险二（迁移）**：把集合关系从提供方一侧改到接入点一侧，预期不改表结构。生成迁移后先看内容，有任何改表操作先停下来报告。
- **环境事实**：前端开发环境地址指向 https 端口，后端须以 `https` launch profile 启动；运行中的主服务会锁输出 DLL，编译前先停、验证完再拉起。用户常自己开着 Vite，不要动。
- **验证链**：build + `dotnet test` + 抓 swagger + `pnpm gen:api` 后看生成层 diff + `pnpm typecheck` 一趟过；SQLite 测试不能替代 MySQL 行为验证。
