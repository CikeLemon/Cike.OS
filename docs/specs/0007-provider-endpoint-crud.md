# Spec: 接入点作为模型提供方的子资源独立增删改查

> **2026-11-27 修订**：本 spec 的「聚合」与「端点」两节已由 [spec 0008](./0008-endpoint-as-aggregate-root.md) 取代——接入点升为聚合根，有自己的端点类、平铺的顶层路由（`/ModelProviderEndpoints`）与单条详情接口，不再寄宿在提供方的端点类里、不再用嵌套路由。接口拆分的来龙去脉与前端 / 测试接缝的由来仍以本文为准。

> Triage: `ready-for-agent`
> 术语遵循根 `CONTEXT.md`（模型提供方、接入点、协议、提供商映射、模型）；结构决策见 `docs/adr/0005-提供商接入点与协议.md`（2026-11-27 修订后的接口形态，取代 spec 0005 中「随提供方整体保存」的部分）；聚合内子实体的写法、校验三层划分见 `Backend/AGENTS.md`。

## Problem Statement

管理者在模型提供方的详情页里维护接入点时，系统没有接入点自己的接口：保存一个接入点，前端必须把「提供方名称 + 名下全部接入点（各带全部映射）」拼成提供方的更新请求整体提交；删除一个接入点，是「提交时带上其余接入点、不带它」。后果：改一个接入点要原样回传没改的接入点（密钥、协议专属设置都在请求里来回传），两个人同时改同一提供方的不同接入点会互相覆盖，提供方的更新契约被接入点细节撑大，读接入点也只能从提供方详情 DTO 里取。

## Solution

模型提供方只管自己的增删改查：DTO 与更新契约只有名称，删除时名下接入点与映射一并删除。接入点作为挂在提供方下的子资源拥有独立的增删改查接口，读写都走它自己的接口；端点方法放在提供方的端点类里。接入点仍是聚合内子实体、不升聚合根：用例加载提供方聚合后，在聚合根的意图方法上添加 / 修改 / 移除接入点。提供商映射继续没有独立接口，嵌在接入点的新建 / 更新请求里随接入点整体同步。

## User Stories

1. 作为管理者，我只修改提供方名称时，其余接入点（包括密钥、协议专属设置与映射）原样保留，以便改名不会误动连接配置。
2. 作为管理者，我在提供方详情页新建一个接入点，一次提交协议、名称、接入地址、密钥、协议专属字段和它的全部模型映射，以便连接与它能提供的模型一次配好。
3. 作为管理者，我编辑某个接入点并保存时只改动这一个接入点，其余接入点不受影响。
4. 作为管理者，我删除某个接入点时，它的提供商映射一并删除，之后这些模型就可以被删除。
5. 作为管理者，接入点删到零个后提供方依然存在，以便先立起供应商再逐步配置。
6. 作为管理者，进入提供方详情页时能看到提供方名称与它的接入点表格（名称、协议、接入地址、支持的模型），以便在一个页面里管理该供应商的全部连接。
7. 作为管理者，我和另一个人同时编辑同一提供方下的两个不同接入点，互不覆盖，以便并行维护。
8. 作为管理者，编辑接入点时协议不可修改，要换协议只能删掉重建，以便协议专属设置不会错位。
9. 作为管理者，更新接入点时我提交的是它的完整模型映射列表：已映射的模型更新分数与提供商侧模型名，新出现的模型新增，没提交的映射删除，以便映射随接入点一次保存。
10. 作为管理者，我在同一个接入点里把同一个模型映射两次时被拒绝且什么都不保存，以便一个接入点对一个模型只有一条映射。
11. 作为管理者，我可以把同一个模型分别映射到同一提供方的两个接入点下，以便同一个模型既能走 OpenAI 兼容、又能走 Anthropic 兼容。
12. 作为管理者，接入点的映射引用了不存在的模型时被拒绝且什么都不保存，以便映射永远指向真实存在的模型。
13. 作为管理者，同一提供方下两个接入点重名时被拒绝，不同提供方下的接入点可以重名。
14. 作为管理者，新建接入点时提交的协议与设置类型对不上时被拒绝，以便保存下来的设置与协议一致；更新接入点时提交的设置类型与它现有的协议对不上时同样被拒绝。
15. 作为管理者，我不填 OpenAI 的组织标识、不填 Anthropic 的 API 版本也能保存接入点。
16. 作为管理者，我删除提供方时它名下所有接入点和映射一并删除。
17. 作为管理者，我对不存在的提供方新建 / 查询接入点时被告知提供方不存在（查询返回 404，写入被拒绝），以便不会把接入点挂到空气上。
18. 作为管理者，我修改或删除一个不属于该提供方的接入点 Id 时被拒绝且什么都不动，以便接入点不会被挪到别的提供方下。
19. 作为管理者，我看不到也不动得了别的租户的提供方与接入点：别的租户的 Id 对我而言一律表现为「不存在」。
20. 作为管理者，接入点列表按名称排序，接入点里的映射按分数从高到低，并且每条映射带模型的显示名称，以便不认识提供商侧模型名的人也能看懂。
21. 作为管理者，接入点列表里每个接入点带着创建时间与更新时间，以便知道连接是什么时候配的、最后一次改是什么时候。
22. 作为管理者，提供方列表页里每个提供方一行，显示它用了哪些协议、支持哪些模型、有几个接入点，这一行为不因接口拆分而变化。
23. 作为前端开发者，我执行 `pnpm gen:api` 后拿到的函数覆盖提供方与接入点的全部端点，以便不手写 URL。
24. 作为前端开发者，编辑接入点的抽屉只依赖提供方 Id 与要编辑的接入点行，不再依赖「整个提供方含全部接入点」的对象，以便组件职责清晰。
25. 作为后端开发者，接入点的新建 / 更新 / 删除经聚合根的意图方法完成，我不在 Handler 里直接增删子实体，以便聚合不变量有唯一的守门处。
26. 作为后端开发者，接入点的新建与更新使用两个输入 DTO，更新 DTO 不含协议，以便协议不可变由契约形状保证而不是靠比对。
27. 作为后端开发者，接入点的重名、引用模型存在等校验集中在用例处理器的单个校验方法里，新建与更新共用，以便规则只写一处。
28. 作为测试者，我能在不手写 URL 的情况下验证接入点四条路由的动词、路径与路径参数绑定（尤其是提供方 Id 与接入点 Id 两个 id 段不串位），以及校验失败与业务拒绝两种 400 形状、列表的 404，以便嵌套路由这种约定路由覆盖不到的写法有自动化保障。
29. 作为测试者，业务规则（重名、模型不存在、映射同步、级联删除）的测试继续从命令 / 查询这一最高点进入，HTTP 测试不重复它们，以便两处接缝各管一段。
30. 作为未来的实现 agent，我拿到本 spec 即可独立完成全部实现（决策均已定稿），不必再做架构裁决。

## Implementation Decisions

### 后端

- **聚合**：接入点仍是模型提供方聚合内的子实体，不升聚合根、不建独立聚合。
  - 聚合根上「按提交的接入点整体同步」的方法被三个意图方法取代：添加接入点、修改接入点（按接入点 Id）、移除接入点（按接入点 Id）。
  - 聚合内部不变量：接入点名称在提供方内互不重复（添加与修改时对着已加载的集合断言，修改时排除自身）；修改 / 移除时接入点 Id 不在名下抛业务异常「接入点不存在」。这些断言依赖集合已加载，用例侧一律连同子集合加载聚合。
  - 接入点子实体的意图方法不变：协议创建后不再变；修改只改名称、接入地址、密钥与协议专属设置；映射按模型为键整体同步（已映射的更新、新出现的新增、未提交的移除），同一模型重复出现在聚合里拒绝。协议专属设置的子类型必须与接入点现有协议一致，仍由子实体断言——更新请求里没有协议，对不对得上只能对着实体上的协议看。
- **仓储**：自定义仓储的「连同两层子集合加载」不变。接入点列表是单个聚合的读取，走它（只读、不跟踪）；提供方列表页的汇总查询仍是投影，不加载聚合，不变。
- **用例**（Application；一类型一文件）：
  - 接入点四个用例：新建命令（提供方 Id + 新建 DTO，处理后带出新接入点 Id）、更新命令（提供方 Id + 接入点 Id + 更新 DTO）、删除命令（提供方 Id + 接入点 Id）、列表查询（提供方 Id，结果为接入点 DTO 列表，提供方不存在时结果为空）。四个用例的处理器独立于提供方的处理器成类，与提供方用例同在模型提供方模块下；校验器同处。
  - 新建 / 更新 / 删除：经自定义仓储连同子集合加载提供方，不存在抛「模型提供方不存在」（不区分「不属于本租户」）；随后调聚合根的意图方法，再保存聚合。
  - 列表：只读加载提供方，不存在返回空；实体到 DTO 交给 Mapster，接入点按名称排序、映射按分数降序，模型显示名称一次批量取回回填，不逐行查库。
  - 校验：新建 / 更新共用一个私有校验方法，只查库一次——映射引用的模型去重后一次 COUNT 核对数量。
  - 提供方用例瘦身：更新只改名，校验只剩名称同租户唯一；DTO 去掉接入点集合；删除仍连带加载子集合后删除（接入点与映射一并软删）。
- **端点**（Service.Open，放在提供方的端点类里）：
  - `GET /api/v1/ModelProviders/{id}/Endpoints`：返回接入点 DTO 列表；提供方不存在返回 404。
  - `POST /api/v1/ModelProviders/{id}/Endpoints`：请求体为新建 DTO，成功返回新接入点 Id（按框架约定 long 序列化为字符串）。
  - `PUT /api/v1/ModelProviders/{id}/Endpoints/{endpointId}`：请求体为更新 DTO，成功返回 200。
  - `DELETE /api/v1/ModelProviders/{id}/Endpoints/{endpointId}`：成功返回 200。
  - 框架的约定路由只能生成「资源 / 方法段 / 单个 id 段」的形状，表达不了嵌套子资源，所以这四个方法各自用框架的显式路由特性指定完整路径与动词（写法沿仓库既有的显式路由端点先例），不手写 `MapXxx`。两个 id 段按参数名绑定到方法参数，提供方 Id 与接入点 Id 的参数名必须与路径段一致。
  - 提供方的 `PUT /{id}` 请求体只有名称；其余五个提供方端点不变。
  - 响应形状沿用现状：FluentValidation 失败是 400 + ProblemDetails，业务异常是 400 + 纯文本消息，只有列表 / 详情取不到返回 404。端点类上的自动校验对两个新输入 DTO 自动生效。
- **DTO**（Application.Contracts）：
  - 新建 `CreateModelProviderEndpointDto`：名称、协议、接入地址、密钥、协议专属设置、映射列表。
  - 更新 `UpdateModelProviderEndpointDto`：名称、接入地址、密钥、协议专属设置、映射列表——**不含协议、不含 Id**。
  - 原「新建 / 编辑共用的保存 DTO」删除。
  - 输出 `ModelProviderEndpointDto` 不变（继承框架审计基类，含 Id / 创建 / 更新时间与人、名称、协议、接入地址、密钥、协议专属设置、映射列表）；映射的输入 / 输出 DTO 不变。提供方 DTO 去掉接入点集合，只剩 Id + 审计字段 + 名称。
- **Validator**（FluentValidation）：
  - 新建 DTO：名称必填且不超过 128；协议在枚举范围内；接入地址、密钥必填；协议专属设置的子类型必须与协议一致；映射列表非 null；映射项沿既有规则（模型 Id 大于 0、提供商侧模型名可省略且不超过 128）。
  - 更新 DTO：同上，去掉协议相关两条。
  - 提供方更新 DTO 的校验只剩名称规则。
  - body 字符串去空白仍由框架负责，Validator / 用例 / 实体里都不写 Trim。
- **数据**：无表结构变更，无 EF 迁移。
- **文档同步**：后端 AGENTS.md 中「聚合内子实体没有独立用例与端点」改写为「子实体不升聚合根，但可以有挂在聚合根端点类下的子资源端点，写操作仍经聚合根的意图方法；嵌套路径用显式路由」；spec 0005 顶部加修订注记指向本 spec。

### 前端

- **API 层**：后端跑起后执行 `pnpm gen:api` 生成，组件只从生成层导入函数与类型，不手写 URL。
- **详情页**：进入时发两个请求——提供方详情取名称与审计信息、接入点列表取表格。新建 / 编辑 / 删除接入点成功后只刷新接入点列表；改名成功后刷新提供方。取不到提供方（404）仍显示「模型提供方不存在或已被删除」。
- **接入点抽屉**：只接收提供方 Id 与要编辑的接入点行（null 为新建）。新建调接入点的新建接口，编辑调更新接口；删除接入点调删除接口。表单字段、协议只读、切换协议二次确认、映射行等交互不变。
- **纯函数层**：删除「提供方整体提交」的拼装函数（更新请求体拼装、接入点转保存项、追加 / 替换、移除）；提供方表单只保留名称表单与「更新请求体 = 名称」；接入点表单的「表单 → 输入」拆成「转新建请求体」（含协议）与「转更新请求体」（不含协议）两个函数。

## Testing Decisions

- **好的测试**只断言可观察行为：保存后读出来是什么、什么被拒绝、HTTP 响应的状态码 / 头 / 体形状；不断言实体私有方法、不依赖 SQL。
- **后端接缝一（既有，业务规则）**：从发布 Command / Query（经本地事件总线）这一最高点进入，SQLite 内存测试宿主，只测外部行为。接入点的用例全部改经它自己的四个用例进入，不再经提供方更新提交完整状态。先例：模型提供方测试类。
  - 接入点：在同一提供方下建两个不同协议的接入点并读回（地址、密钥、专属设置子类、未填时为 null）；编辑不改协议且其余接入点原样；重名拒绝且不保存；跨提供方重名放行；修改 / 删除不存在的接入点 Id 被拒；删到零个后提供方仍在；删除后其映射不再阻止模型删除。
  - 映射：同一接入点重复映射同一模型拒绝；同一模型挂同一提供方的两个接入点放行；引用不存在的模型拒绝且不保存；更新接入点时映射整体同步（更新 / 新增 / 移除）。
  - 归属：对不存在的提供方新建 / 查询 / 修改 / 删除；别的租户的提供方 Id 与接入点 Id 一律按「不存在」处理。
  - 提供方：只填名称创建；改名后接入点原样；删除提供方后接入点与映射不可查；提供方详情不再带接入点。
  - 校验器：新建 DTO 的协议与设置不匹配被拒；更新 DTO 的基础规则；提供方更新 DTO 只有名称规则。先例：既有的 DTO 校验器测试。
- **后端接缝二（新增，HTTP 形状）**：仓库此前没有 HTTP 测试基础设施，本 spec 新建一处——用 ASP.NET Core 的测试宿主工厂启动真实主服务入口（同一管线、同一路由映射、同一 JSON 约定），数据库换成一个保持打开的 SQLite 内存连接，运行环境为 Development（主服务在非开发环境才要求认证），事务保持开启（与真实运行一致），启动后建表。
  - 引入测试专用的 ASP.NET Core 测试宿主包；主服务入口对测试程序集可见。
  - 只测 HTTP 层才看得到的东西，不重复接缝一的业务规则：四条路由各自的动词与路径；两个 id 段不串位（改 / 删路由里提供方 Id 与接入点 Id 各绑各的）；新建返回的 Id 是字符串；校验失败 400 + ProblemDetails；业务拒绝 400 + 纯文本；提供方不存在时列表 404；租户上下文按框架租户解析中间件的默认约定传入后隔离生效。
  - 风险与处理：这是仓库首个起宿主的测试。主服务入口带文件日志与技能包存储等开发期装配，测试环境用临时目录承接；Redis 相关的包只被引用、启动期不连接。若启动失败，优先在测试宿主里替换配置或服务，不为测试改生产代码。
- **前端**：纯函数接缝（vitest）——接入点表单转新建 / 更新请求体（按协议组装设置、未填专属字段为 null、映射行转提交项、更新请求体不含协议）、前端自身校验、提供方名称表单与更新请求体；路由表用例不变。浏览器走查兜底：新建提供方 → 跳详情 → 新建两个不同协议的接入点 → 编辑其中一个 → 删一个 → 删到零 → 改名后接入点仍在 → 删除提供方。
- **验收**：`dotnet build` 0 警告、`dotnet test` 全绿；`pnpm gen:api` 后 `pnpm build`（含 vue-tsc）与 `pnpm test` 通过；生成层里接入点四条函数存在、提供方更新请求体类型不含接入点。

## Out of Scope

- 提供商映射的独立接口（映射继续随接入点）。
- 提供方列表页及其汇总 DTO 的任何改动。
- 接入点的连通性测试、从供应商 API 拉取模型清单。
- `ApiKey` 读取侧脱敏与「留空表示不修改」。
- 调用路由的运行时执行链路。
- 新增协议及其专属字段。
- 其他聚合（如工具包下的工具）是否照此拆子资源接口。
- 模型、标签、权限体系的任何改动。
