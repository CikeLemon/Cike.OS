# Spec: 领域实体 EF Core 映射补齐

> Triage: `ready-for-agent`
> 术语遵循根 `CONTEXT.md`（本 spec 交付时将补录实体域术语：Agent、模型、模型提供方、工具、工具包、工具包分类、标签、会话及成员/消息/事件/文件、用户工具配置、Agent 工具包绑定与 Agent 工具）。

## Problem Statement

领域层已有 15 个实体建模完毕，但 EF Core 映射层只为其中 2 个（工具、用户工具配置）提供了显式配置，DbContext 也只注册了这 2 个 DbSet。其余 13 个实体处于「半配置」状态：任何一次建库或迁移都会落入 EF 默认约定（字符串默认无长度上限、无索引、主键生成策略与项目约定相悖），多租户与审计基类也不统一（三个实体缺软删，两个缺租户）。后续任何用例开发都要先还这笔映射债。

## Solution

按项目既有 DDD 约定，一次性补齐全部实体的 EF Core 映射：对齐三个「半审计」实体的领域基类（升聚合根 / 补软删 / 补多租户），按聚合域分组落成四份映射配置，DbContext 注册全部 DbSet；以 SQLite 内存库上的全实体冒烟测试锁住配置可运行性；同时以 ADR 固化「索引非唯一与软删共存」的设计决策，并把实体域术语补进领域术语表。不生成迁移。

## User Stories

1. 作为后端开发者，我新增任何实体用例时该实体已有显式映射可用，以便不必先补 EF 配置再写业务。
2. 作为后端开发者，我在 SQLite 内存测试库上建库成功，以便集成测试不受 MySQL 依赖拖累。
3. 作为后端开发者，我读到某个实体的映射时能在对齐的域分组文件里一次看全该域（Agent 域、会话域、模型域、工具域），以便不用在 15 个单实体文件间跳转。
4. 作为后端开发者，现有的工具与用户工具配置两份单实体映射被并入工具域分组文件且行为不变，以便映射风格全仓唯一、没有新旧混排。
5. 作为后端开发者，我给实体做软删删除时软删过滤器对全部 15 个实体行为一致，以便不出现「删了但查得出来」的例外实体。
6. 作为后端开发者，多租户过滤器覆盖全部业务实体（含 Agent 工具绑定域三个实体），以便租户隔离没有静默漏洞。
7. 作为后端开发者，Agent 工具包绑定与其子项 Agent 工具构成标准聚合（聚合根 + 子实体 + 级联删除），以便硬删兜底与子集合加载符合 DDD 预期。
8. 作为后端开发者，会话成员知道自己属于哪个会话（外键已补齐），以便成员查询与归属校验有据可依。
9. 作为后端开发者，消息的发送者角色（含 Microsoft.Extensions.AI 的 ChatRole 类型）能正确持久化与读回，以便对话域用例可直接落库。
10. 作为后端开发者，Agent 的推理选项、模型提供方的多态连接设置、模型的标签 ID 集合以 JSON 列存储且 round-trip 无损，以便值对象持久化不需要逐表拆列。
11. 作为后端开发者，所有主键遵循「应用侧生成、数据库不自动生成」约定，以便雪花/程序赋值策略不被数据库自增破坏。
12. 作为后端开发者，字符串列有显式长度声明、外键列都有独立索引，以便 MySQL schema 落地时即符合团队约定。
13. 作为维护者，业务键（如标签键、工具包编码）重复插入不会被唯一索引拒绝，以便软删后同键可重建——这个取舍有 ADR 记录，不被后人当 bug「修掉」。
14. 作为维护者，15 个实体各完成一轮插入/读回冒烟测试，以便任何配置回归（值转换器、JSON 列、级联关系）在 CI 就暴露。
15. 作为维护者，领域术语表收录了本次涉及的实体域词汇，以便后续 spec 与代码讨论有共享语言。
16. 作为维护者，AGENTS.md 的实体映射指引反映当前按域分组的现状，以便后续 agent 不按过时说明放错文件。
17. 作为未来的实现 agent，我拿到本 spec 即可独立完成全部实现（决策均已定稿），不必再做架构裁决。

## Implementation Decisions

- **领域基类对齐（三处 Domain 层修改）**：Agent 工具包绑定由审计实体升为完整审计聚合根（持有子集合故为聚合根）；Agent 工具由审计实体升为完整审计实体并补多租户；模型实体由审计实体升为完整审计实体（租户已有）。会话成员的会话外键已由用户补齐，不再动。
- **映射文件按聚合域分组**：四组——Agent 域（Agent、Agent 工具包绑定、Agent 工具）、会话域（会话、会话成员、会话文件、会话消息、会话消息事件）、模型域（模型、模型提供方、标签）、工具域（工具、工具包、工具包分类、用户工具配置）。每组一个文件、内部逐实体一个配置类；现有两份单实体映射迁入工具域文件后删除原文件，行为不变。
- **DbContext**：补齐其余 13 个 DbSet；仍从程序集扫描应用配置。
- **主键**：全部 `ValueGeneratedNever`，沿用既有约定。
- **值转换**：Agent 推理选项、模型提供方连接设置（多态）、模型标签 ID 集合走 JSON 序列化值转换 + `json` 列类型（对齐既有两份映射的做法）；消息发送者角色（ChatRole）转字符串存储。
- **字符串长度**：短标识 64、名称 128、描述 512、长文本（指令、自述、事件内容、JSON schema 描述等）不设限；具体逐属性取值在实现 review 中把关。
- **索引**：外键列一律单独建索引；**全部索引非唯一**——软删与唯一索引语义冲突，取舍以 ADR 固化（见 Further Notes）。
- **关系**：仅 Agent 工具包绑定 → Agent 工具配置 required 聚合内一对多 + 数据库级联删除（软删聚合时子项由应用层同事务清理）；其余实体间不加导航属性、不建 EF 关系，只保留外键字段 + 索引，Domain 层零额外膨胀。
- **文档**：新建 ADR 记录「索引非唯一与软删共存」的决策；领域术语表补录实体域词条（仅领域语言，无实现细节）；AGENTS.md 仅更新实体映射放置说明的过时括注，Subject/用户/权限相关行不动（已独立成服务、后续以服务间调用对接）。

## Testing Decisions

- **原则**：只测外部行为——实体经 DbContext 插入后能原样读回（含值转换器输出），不测配置内部写法。
- **接缝**：复用现有最高接缝——测试宿主的 SQLite 内存库（既有先例：用户工具配置的集成测试同走此宿主）。不新建接缝。
- **新增一个冒烟测试**：15 个实体各插入一条并读回断言，覆盖建表、JSON 列、ChatRole 转换、多态设置反序列化、聚合子集合级联。这是配置从「编译过」到「运行过」的唯一自动化保障。
- **回归**：现有测试套件（含用户工具配置用例与校验器测试）必须全部通过。

## Out of Scope

- 首次迁移的生成（独立步骤，届时确认 MySQL 环境）。
- 唯一索引的引入（已裁决放弃，见 ADR）。
- Subject / 用户 / 角色 / 权限相关实体——已拆分到独立服务，后续以服务间调用对接，本仓不处理。
- 任何 Application 层用例、Service.Open 端点、前端改动。
- 工具参数值解析领域服务等既有逻辑的改动。
- 为实体间补导航属性（等具体查询用例出现再加）。

## Further Notes

- 本 spec 由一次完整的设计拷问会话定稿，全部实现决策（分组边界、基类对齐、非唯一索引、级联策略、测试接缝、迁移缓行）均经用户逐项确认；实现时无需复询。
- 关键既定决定（变更需与用户复确认）：索引一律非唯一；Agent 工具包绑定升为聚合根；映射按聚合域四文件分组；不生成迁移。
- 发布方式：本仓库尚未配置 issue tracker（`docs/agents/issue-tracker.md` 缺失、本机无 gh CLI），沿用 spec 0001 的落盘先例，以仓库内 markdown + 头部 `ready-for-agent` 标注代发布。
