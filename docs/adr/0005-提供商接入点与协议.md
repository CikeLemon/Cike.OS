# 提供商接入点与协议：连接下沉到接入点，映射归接入点

同一家供应商会同时提供多种协议的端点（智谱既有 OpenAI 兼容端点，也有 Claude / Anthropic 兼容端点），而原设计里一个模型提供方只有一份连接设置、类型创建后不可变，要接第二种协议只能再建一个同名提供方，「供应商」这个分组就散了。决定：**模型提供方收敛为一个名称；连接（协议 + 地址 + 密钥 + 协议专属字段）下沉为聚合内子实体「接入点」，提供商映射归接入点**；原来的 `ModelProviderType` 正名为「协议」——它是「怎么讲」，不是「谁」。

> 2026-11-27 修订：接口形态由「接入点随提供方整体提交」改为「接入点作为提供方的子资源独立增删改查」。当时否决子资源路由是误读了「合并进 ModelProviderService」的意思，见 Considered Options 后两条。
>
> 2026-11-27 再修订：聚合结构由 [ADR 0006](./0006-接入点升为聚合根.md) 取代——接入点升为聚合根，映射继续做它的子实体，三层聚合拆成两个两层聚合。本文「聚合变为三层」「聚合连同两层子集合的加载走自定义仓储」两条及「三层聚合是首例」的说明以 ADR 0006 为准。

## Considered Options

- **保持「提供方 = 一条连接」**（New API 的渠道、LiteLLM 的 `model_list` 都是这个形态）：结构零改动，但同一供应商在列表里出现多行，供应商这一层分组只能靠命名约定。
- **提供方持 `Setting[]` 值对象数组，映射靠下标或另造的键指向其中一条**：值对象没有身份，下标在编辑重排后会错位；给它造了稳定标识之后，它事实上已经是子实体。
- **协议专属字段平铺成接入点的列**：每加一种协议就要一次迁移，契约上会把所有协议的字段一起暴露出来。（MySQL 行上限不构成理由：可空列存 NULL 只占约 1 字节。）
- **映射留在提供方上，调用时再按协议挑接入点**：映射与连接脱钩，而同一个提供商侧模型名在不同协议下含义可能不同，没有地方落。
- **接入点读走提供方 DTO、写走子资源接口**（第一版实现）：读写不对称，读到的接入点与改它走的不是同一个入口。
- **接入点随提供方整体提交（`UpdateModelProviderDto.Endpoints` 带全部接入点，没有接入点自己的接口）**（第二版实现）：改一个接入点要页面把其余接入点原样拼回去，两个人同时改同一提供方的不同接入点会互相覆盖；提供方的更新契约被接入点细节撑大。
- **在 Application 层写静态加载器：先带接入点查聚合根，再在同一 DbContext 查映射、靠 EF 关系修正挂回集合**（第一版实现）：加载靠隐式行为，读代码的人要靠注释才知道「查了不用」是有意的；三层聚合的加载应当是仓储的职责。

## Consequences

- 聚合变为三层：`ModelProvider → ModelProviderEndpoint → ModelProviderMapping`。接入点名称同提供方内唯一（聚合内部不变量，在聚合里断言）；**一个接入点对一个模型只映射一条**是聚合不变量，同一模型可以挂在同一提供方的多个接入点下；接入点之间不做去重（同协议、同地址、不同密钥都合法）；提供方可以没有任何接入点。
- 接入点的协议创建后不可变；协议专属设置是多态值对象，其子类型必须与协议匹配（聚合不变量，写法同 `Tool`）。地址与密钥是接入点自己的字段，值对象只装协议专属字段（现均为可选）。ADR 0003「值对象直接作为 API 契约」不变。
- 管理入口：模型提供方有详情页，接入点在其下逐个维护，一个表单同时包含连接信息和该接入点的全部映射；映射仍然没有独立入口。
- 接口形态：提供方只管自己的增删改查（DTO 与更新契约只有名称）；接入点是挂在提供方下的子资源，读写都走它自己的接口——`GET /ModelProviders/{id}/Endpoints`、`POST /ModelProviders/{id}/Endpoints`、`PUT|DELETE /ModelProviders/{id}/Endpoints/{endpointId}`，端点方法放在提供方的端点类里。接入点仍是聚合内子实体、不升聚合根：用例加载聚合根后在它的意图方法上添加 / 修改 / 移除接入点，映射随接入点整体同步；协议不可变靠更新契约不含协议来保证。
- 聚合连同两层子集合的加载走自定义仓储 `IModelProviderRepository`（实现里两级 `Include`），不靠 EF 关系修正的隐式挂接。
- 删除语义：删接入点连带其映射；删提供方连带全部接入点与映射；删模型时任一接入点下还有映射指向它则拒绝。
- 路由：调用某个模型时，同租户所有接入点的映射放在一起按分数取最高，接入点之间平等；同分如何取舍留给运行时实现。
- 迁移：在 `20261126040120` 之后新增 EF 迁移——`ModelProviders` 去掉设置列，新增 `ModelProviderEndpoints` 表，`ModelProviderMappings` 的外键列由指向提供方改为指向接入点；dev 库旧数据直接删除，不写数据迁移。**应用该迁移前必须先清空 `ModelProviderMappings` 与 `ModelProviders`（含已软删的行）**：迁移是把映射外键列改名而非重建，存量映射行里的值是提供方 Id、指向不存在的接入点，加外键时会失败。
- 三层聚合在仓库里是首例，孙实体的 Id / 租户 / 软删行为在落地前先用冒烟测试验证。
- 枚举 `ModelProviderType` 改名 `ModelProviderProtocol`，JSON 判别值（1 / 2）不变。ADR 0004 中「ModelProviders 表结构不变」「映射是提供方的子实体」「一个提供方对一个模型只映射一次」「映射在提供方表单里维护」四条由本决策取代。
