# 对话以消息表为上下文真源，框架 AgentSession 状态独立成表

对话上下文（单聊与群聊统一建模，共用一套消息/事件/附件表，群聊另加对话群与成员表）以对话消息表为唯一真源：界面展示、续聊恢复、喂给框架的历史都从消息表回放（实现框架 ChatHistoryProvider）。一轮一行消息（谁、什么角色、什么时候说的这一轮），轮内输出的内容块（思考、文字、图片、工具调用、工具结果、审批等）逐行追加在事件表，**每行存一个块**：框架有的块（text/reasoning/data/functionCall/functionResult/usage 等，$type 判别）载荷直接存框架原生 AIContent JSON，平台特有块（如工具审批）存自定义信封 JSON；回放时按轮分组事件行、拼回框架 ChatMessage。框架 AgentSession（每个 Agent 安装在对话内的运行时内部状态，如挂起的工具审批）是另一类东西：按对话 × Agent 安装一行、以框架序列化 blob 原样落库（平台自研 MySQL 版 AgentSessionStore），不解析。分家的理由：实跑验证框架默认内存历史会随轮次在 blob 内膨胀（消息不可索引、展示需解析 blob），而多实例部署要求任一服务器凭对话 ID 即可重建全部状态——两者都必须在库里，但「给用户看的内容」与「给框架续跑的状态」各归其位。群聊成员何时发言由编排者决定（对应框架 GroupChatManager 的选举钩子，编排 Agent 安装看历史选下一个发言者），编排者自身的运行状态同样以对话级 blob 原样落库。

## Considered Options

- 对话表塞框架序列化 blob、历史留在 blob 内：实跑证明历史随轮次膨胀，消息不可查询、界面展示还得解析 blob，等于消息表降级为展示投影，与「消息 = 恢复上下文与界面展示的载体」冲突。
- 只存消息、完全不存 AgentSession 状态：无审批流时可行，但「等待用户批准的工具调用」等框架内部状态丢失后，恢复的 Agent 行为错乱；多实例/重启不可靠，已明确要求落库。
- 服务器粘性会话（内存 session + 路由固定实例）：重启即丢、扩容受限；调研的同类开源（LangGraph checkpointer、Dify、LobeChat、Rasa tracker store）均为无状态服务 + 共享存储，无一采用。
- 步级 checkpoint（LangGraph 式每执行步落库）：恢复粒度过细、存储成本高；轮级重试（读已落库状态重开一轮）已覆盖产品语义，步级续跑留待工作流引擎线。
- 一行消息存整条 contents 数组（本 ADR 初版方案）：流式追加要整列读改写，审批等平台块没有框架类型可套，按块类型检索/渲染得解析 JSON；改为块行逐条追加。
- 事件行存 AIContent 数组：块是「轮内输出的最小单位」，数组没有职责；数组只在回放拼 ChatMessage 时出现在内存里。
