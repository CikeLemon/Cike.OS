# 索引一律非唯一：与软删共存

全部实体的数据库索引（含业务键如 `Tag.Key`、`Tool.Code`、`ToolPackage.Code`、复合索引 `(TenantId, UserId, ToolId)` 等）一律不设唯一约束。原因：实体普遍走软删（`IsDeleted`），唯一索引会阻止「软删后同键重建」——例如删除 `Tag(tenant, "vision")` 后无法再创建同名标签，除非先物理清理历史行。业务键查重由应用层（Command Handler 先查再写）承担，接受并发窗口。

## Considered Options

- **唯一索引 + 过滤索引（`WHERE IsDeleted = 0`）**：MySQL 8 不支持过滤索引，排除。
- **唯一索引 + 软删时改键（如追加 Id 后缀）**：污染业务键，读侧需反向处理，排除。

## Consequences

- 重复键可能在并发插入下落库；需要强一致的业务键唯一性时，未来须引入数据清洗 + 唯一索引（或改用 MySQL 之外支持过滤索引的存储），属于破坏性变更。
- 「同键多条有效记录」是脏数据信号，应由对账/查询侧容忍或告警，而不是靠数据库约束兜底。
