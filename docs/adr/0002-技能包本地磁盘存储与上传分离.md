# 技能包存储：本地磁盘解压目录，上传与表单提交分离

技能形态工具依赖一整个目录的文件（技能包）。项目与 Cike.Framework 均无文件存储能力，我们决定把技能包以 zip 单文件上传，由服务端解压到本地磁盘 `{RootPath}/{tenantId}/{guid}` 目录，`SkillToolSetting.Directory` 只保存相对存储根的路径；上传是独立接口（返回目录路径），工具表单提交是纯 JSON。本地磁盘解压 + 路径引用是与存储实现无关的最小方案，日后换对象存储只需替换存储实现，领域层语义不变。

## Considered Options

- **浏览器目录上传（`webkitdirectory` 多文件）**：一次请求携带几十上百个带相对路径的文件，失败时半途残留、大目录浏览器易卡，排除。
- **表单字段 + zip 打成一个 multipart 请求在保存时提交**：工具设置是三形态多态 DTO，混入文件后 Validator / Command / `gen:api` 客户端都要走 multipart 特例，排除。
- **对象存储（MinIO / 云 OSS）**：引入新基础设施依赖，当前单机部署阶段收益不抵成本；接口按「存储实现可替换」设计，保留升级路径。
- **上传目录以 toolId 命名**：上传时工具尚不存在，需先落临时目录再搬迁的两阶段流程；改用 guid 目录，编辑重传天然不覆盖。

## Consequences

- 上传后放弃表单会留下孤儿目录，本期不回收；需要时另加对账清理任务。
- 目录删除（编辑重传后删旧目录、删除工具时删目录）是尽力而为，失败只记日志，不阻断业务事务。它在事务提交前执行：残余窗口是「SaveChanges 成功、COMMIT 瞬间失败」——此时旧目录已删而数据库回滚仍指向它，造成引用悬空。框架没有提交后钩子（领域事件在提交前 drain、补偿不覆盖提交失败、后台事件无顺序保证），彻底消除需要「目录先进 trash、端点在 PublishAsync 返回后再 purge」的两阶段方案；评估后认为窗口极小、暂不做，接受为已知项。
- 删除只接受 `skills/{当前租户}/{guid}` 形式的路径：根目录、租户目录、跨租户路径一律拒删（Directory 来自客户端输入，不能据此删整根或别人的目录）。
- 多实例部署时本地磁盘需共享卷或改对象存储，否则文件不互通。
- zip 解压必须做 zip-slip 路径穿越防护、大小上限、以及包根 `SKILL.md` 存在性校验（技能包格式约定）。
