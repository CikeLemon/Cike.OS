# 对话（Conversation）相关实体与会话运行时基建

## Problem Statement

使用方（租户用户）目前没有任何方式与已安装的 Agent 持续交流：没有对话记录可供回看，Agent 无法跨请求接续上下文，平台也无法对 Agent 调用做计量与排障。同时，多 Agent 协作（群聊）这一 AI Native 场景完全没有承载结构。

## Solution

为平台建立「对话」域的实体与运行时基建：单聊与群聊统一建模的对话表、按序追加的消息表（作为上下文唯一真源）、追加式事件表（计量排障）、附件表、以及按「对话 × Agent 安装」落库的框架 AgentSession 状态表。恢复上下文通过平台的 ChatHistoryProvider 实现从消息表回放喂给框架；框架会话状态通过自研 MySQL 版 AgentSessionStore 落库，使服务实例无状态、任一实例凭对话 ID 即可完整接手。群聊由对话群与成员表承载，成员何时发言由编排者（默认为编排 Agent 安装看历史选举）决定。

## User Stories

1. 作为使用方，我想与某个已安装的 Agent 安装开始一段对话，以便以聊天方式向它发起任务
2. 作为使用方，我想看到自己的对话列表（含标题），以便找到并回到之前的对话
3. 作为使用方，我想对同一个 Agent 安装开多段并行对话，以便按主题分头推进
4. 作为使用方，我想在对话中看到完整历史（我的输入、Agent 回复、工具调用与工具结果），以便理解 Agent 做了什么
5. 作为使用方，我想在消息里携带附件，以便把材料交给 Agent 处理
6. 作为使用方，我想收到 Agent 生成的文件（生成物），以便下载结果
7. 作为使用方，当一轮失败时我想看到失败原因并点击重试，以便任务继续推进
8. 作为使用方，我想无论请求落在哪台服务器都能继续对话，以便服务故障或重启不影响我
9. 作为使用方，我想删除自己的对话，以便清理不保留的内容
10. 作为使用方，在 Agent 等待我批准工具调用期间，对话跨请求/重启恢复后审批状态仍然有效，以便流程不中断
11. 作为使用方，我想创建对话群并拉入多个 Agent 安装与其他用户，以便多 Agent 协作处理同一任务
12. 作为使用方（群主），我想往群里增删成员（用户与 Agent 安装），以便调整协作阵容
13. 作为使用方，我想在群里 @某个成员 Agent 安装，以便显式指定它响应
14. 作为使用方，我想让编排 Agent 安装看对话自动决定谁接话，以便不必手动指挥协作
15. 作为使用方，我想看到群里每条消息标明是哪个成员说的，以便理解协作过程
16. 作为租户管理员，我想查看租户内的对话计量（谁、何时、哪个 Agent 安装、模型、Token、耗时、成败），以便成本与使用管理
17. 作为租户管理员，我不应能查看用户与 Agent 的对话明文，以便保护用户隐私（沿用用户工具配置的隐私口径）
18. 作为租户管理员，我想查看事件级失败原因（技术错误信息，非对话内容），以便排障
19. 作为运行时，我想把框架 AgentSession 内部状态按「对话 × Agent 安装」落库，以便任一实例恢复后 Agent 行为不漂移
20. 作为运行时，我想从消息表回放历史喂给框架，以便续聊不依赖第二份历史
21. 作为运行时，我想保证同一对话同一时刻只有一轮在执行，以免并发写坏消息顺序与会话状态
22. 作为编排者，我想每轮看对话历史选举下一个发言的成员，以便群聊自然推进
23. 作为编排者，我想判断群聊何时终止，以便不无限循环

## Implementation Decisions

- 统一语言采用「对话（Conversation）」（对应框架 AgentSession 的载体），词汇表已更新（对话、对话群、编排者、对话消息、轮、对话事件、对话 Agent 会话状态七个词条）。
- 七张表，全部遵循后端既有约定（long 主键应用侧生成、审计基类、多租户、软删、枚举进 Domain.Shared、EF 显式映射、迁移仅由 dotnet ef 生成）：
  - **Conversation**：形态（单聊/群聊）；单聊挂发起用户与 Agent 安装；群聊挂对话群；标题；编排者运行状态（JSON 列，可空，单聊恒空）。
  - **ConversationGroup**：群名、群主用户、编排模式（编排 Agent 安装 / 成员提及 / 顺序轮流，枚举三档建齐、编排 Agent 为主档）、编排 Agent 安装 Id（编排模式为编排者时必填）。
  - **ConversationGroupMember**：群、成员类型（用户 / Agent 安装）、成员 Id；建群即同时创建对应 Conversation（群与对话一对一）。
  - **ConversationMessage**：对话、所属轮（用户手输为空）、发送者类型与 Id、角色（user/assistant/tool）、内容块 JSON（框架原生格式、含 text/functionCall/functionResult 等 $type 判别块，原样存不拆列）、对话内递增顺序号（对话+顺序号唯一索引）。
  - **ConversationEvent**：对话、轮、Agent 安装、事件类型（开始/完成/失败/取消）、重试指向原轮、模型、输入/输出/总 Token、耗时、错误信息；追加式不可变。
  - **ConversationFile**：所属消息、种类（用户附件 / Agent 生成物）、名称、大小、MIME、存储标识；内容进文件存储不入库。
  - **ConversationAgentSession**：对话 + Agent 安装唯一，状态列存框架序列化 blob 原样，平台不解析。
- 需先补 **AgentInstallation** 实体骨架（租户、Agent 定义、绑定的模型）——对话表的外键依赖它，当前该实体不存在。
- 平台实现框架 **AgentSessionStore** 的 MySQL 版（存/取/删三方法，upsert 行级）；框架没有现成 MySQL/EF 实现（官方仅有 InMemory、Azure Blob、Foundry、Noop）。
- 平台自建 **ChatHistoryProvider**：从消息表按顺序号回放为框架 ChatMessage 序列；消息表是对话上下文的唯一真源（详见 ADR 0002）。
- 消息**轮末整批落库**（框架调用结束钩子时机，批量插入）；流式期间靠推送展示不落库；崩溃轮消息不落库、事件记失败。
- 重试语义为**轮级**：读已落库状态，以原输入重开新的一轮，事件通过「重试指向原轮」关联；不做步级续跑。
- 群聊接入框架 **GroupChatManager** 编排抽象：编排 Agent 安装包装为「看历史选举下一个发言者」的实现（SelectNextAgentAsync）；成员提及解析显式指定；顺序轮流仅作枚举占位。编排者自身状态以对话级 blob 原样落库（对话表的编排者状态列）。
- 并发控制：同一对话同一时刻仅一轮（Redis 分布式锁，技术栈现成）。
- 隐私与产品语义（已拍板）：管理员不可见对话明文（仅事件计量）；消息不撤回不编辑（历史不可变）；单聊允许多段对话（对话列表形态）；对话永久保留、删除为软删。
- 用例走 Application 层 Command/Query + 事件总线 Handler 的既有模式，对外仅保留 DTO 契约。

## Testing Decisions

- 只测外部行为，不测实现细节：端点契约、表结构约束、框架接缝的往返行为；不测内部私有方法。
- 主缝隙为现有最高缝隙：Service.Open 的 HTTP 集成测试（隔离 SQLite 内存库），沿用现有测试工程的组织方式——对话 CRUD、群与成员管理、消息回放、事件记录、隐私边界（管理员请求明文被拒）都在这一层断言。
- 仅有的两个新缝隙均为框架自带抽象的实现测试：MySQL 版 AgentSessionStore（存/取/删往返、按对话×Agent 安装隔离）、ChatHistoryProvider（从消息表按顺序号回放出框架 ChatMessage，工具调用/工具结果内容块保形）。用假 ChatClientAgent 做序列化取证，不依赖真实模型。
- 真实模型调用与编排 Agent 的真实 LLM 决策不在测试范围（外部依赖）。

## Out of Scope

- 真实模型调用链路（模型服务连通、编排 Agent 的真实推理质量）
- 步级 checkpoint / 工作流引擎（Magentic 完整模式：计划账本、重规划）
- 消息撤回与编辑
- 管理员查看对话明文（隐私口径已否决）
- 对话/消息的定期清理与归档策略
- Agent 可用范围数据权限（归统一认证中心）
- 前端管理界面实现（本 spec 只定实体与 API 契约）
- 流式期间的断线重连细节（首期断线等轮末）

## Further Notes

- 关键决策记录于 ADR 0002（对话以消息表为上下文真源，框架 AgentSession 状态独立成表），含被否选项：blob 内留历史、完全不存 AgentSession、粘性会话、步级 checkpoint。
- 框架侧证据来自本地仓库源码调研与探针程序实跑（消息 JSON 形状、session blob 形状、未注册工具调用被自动回填错误结果的行为）；框架版本与 NuGet 正式版对齐。
- 词汇表与 ADR 已先于本 spec 落盘，实现时以它们为准。
